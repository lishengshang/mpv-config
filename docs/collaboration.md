# 跨工具共享上下文与纠错

## 共享信息放在哪里

工具自己的聊天、记忆和隐藏目录可以辅助工作，但不能作为唯一交接。把接手必需的信息写进仓库，由 Git 保存版本：

| 文件 | 用途 |
| --- | --- |
| `AGENTS.md` | 开发约束：怎样改、怎样验证 |
| `PROJECT_STATE.md` | 当前进度、证据、已知问题、任务入口 |
| `docs/tasks/<任务ID>.md` | 谁负责、改了什么、做到哪里、如何继续 |
| `docs/decisions.md` | 选择某方案的理由、边界，以及被替代的旧决策 |
| Git 提交与 diff | 实际变更内容、版本与回退依据 |

共享文件只保存简明事实、决定和验证证据，不复制整段聊天，不写私密信息。真实代码行为与可复现结果优先；文档与代码不符时先登记差异，再按授权需求修正代码或记录。

## 每个工具都要有入口

在 Trae、Zcode、WorkBuddy、GPT 的项目指令中引用同一个入口，或每次新会话粘贴下方提示。具体工具是否支持自动加载、规则文件名和路径，需要在该工具中确认；本流程不依赖这种支持，也不重复维护四套完整规范。

```text
这个仓库由多个 AI 工具共同维护。开始前读取 AGENTS.md、PROJECT_STATE.md、
docs/collaboration.md、docs/decisions.md 及本次任务记录。
先核对 git status、分支、HEAD 和相关 diff，报告你理解的当前进度与未验证项。
以仓库代码和验证证据为准，不把私人记忆当成项目事实。
为本次工作创建或接续 docs/tasks/<任务ID>.md，登记所有者、状态和可写文件。
不要覆盖他人的在途改动。结束前更新任务交接；若你负责集成，同时更新 PROJECT_STATE.md。
本次任务：<需求>。任务ID：<ID>。你负责的文件：<范围>。
```

没有仓库访问能力的聊天工具，需要获得当前共享记录和相关 diff 的副本；它的建议由有仓库访问权限的工具核对并落盘，不能自动视为已经实施。

## 开始、交接与并行

任务状态使用：`待处理 → 进行中 → 待验证 → 已完成`，另有 `受阻` 和 `已替代`。已完成需满足任务验收；文档任务只需文档检查，播放任务需对应运行证据。

开始时登记工具/会话标识、日期、分支、起始提交、目标、文件范围与验收条件。暂停或切换工具时记录最后完成步骤、未提交文件、命令结果和下一条具体操作。接手者先核对实际情况，再写入交接记录；不能因为超时或旧工具无回复自行宣布其任务已释放。

同一个工作区内每个文件只安排一个写入者；任务文件是协调记录，不是操作系统锁，必须由用户或集成人确认分配。并行工具分别写自己的任务文件，共享状态与决策汇总由集成人维护，避免连交接文件也相互覆盖。

跨机器或独立 worktree，未提交改动不会靠 Git 自动传递。交接使用已授权的提交，或补丁加新文件包；接收者检查版本与完整性。被忽略的机器配置和运行依赖单独准备，不把私人配置作为共享包发布。

## 发现错误时如何纠正

1. 在任务记录或共享问题表登记问题 ID、预期/实际行为、复现步骤、相关文件与证据。将猜测标为待确认。
2. 能复现时确认影响与原因；无法复现时保留环境差异及待验证状态。
3. 明确修复所有者与可写范围，做最小修复；必要时依据 diff 定点撤销，避免覆盖无关改动。
4. 运行复现步骤和相关回归，把命令、环境、结果与证据写回任务。
5. 修复验证后更新共享状态。若旧决策导致问题，在 `docs/decisions.md` 将其标为已替代并链接新决策，避免下一个工具再次按旧理由改回去。

例如 VS 自检误报：先登记 `CHECK-001`，制作“进程非零退出/日志缺失”的复现场景，再修改检查逻辑，确认这些场景都返回失败，最后验证正常滤镜仍可通过。只修文档不能将此问题关闭。

## 防止记录失效

- 每条完成结论附验证范围和提交号；未提交时明确写出路径及状态。
- 起始提交变化或相关文件被其他工具修改时，重新核对，不沿用旧的通过结论。
- 任务交接保留按日期追加的简短历史；当前状态可更新，失败证据和被替代决策不静默删除。
- 文件约定无法保证工具服从。后续把可机械检查的规则写成验证脚本与 CI；用户或集成人负责确认任务交接确实发生。
